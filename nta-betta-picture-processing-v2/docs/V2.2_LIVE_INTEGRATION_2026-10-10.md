# Betta V2.2 — live integration, QA analysis, and supervised acceptance

Status: CODE COMPLETE + TESTED (offline). NOT ACTIVATED. Live paid generation and
live Shopify writes are disabled. This document records the integration, the
historical QA-exception analysis, and the supervised-acceptance / activation plan.

## 1. Real adapter integration (`scripts/betta_adapters.py`)

`make_adapters(...)` wires `betta_process.process_batch` to the existing components.
No generation engine, uploader or archive system was reimplemented.

| Stage | Reuses |
|---|---|
| intake | `betta_watch.scan` + `ProcessedRegistry`, copies into `<batch>/intake`, hashes |
| identify | `vision_review.py --mode catalogue` + `label_identity` normalisation |
| generate | existing `grok_hero.py` (unchanged engine/prompt/model) |
| finish | existing `render_betta_label.render` |
| qa | `vision_review.py --mode qa` + deterministic wrapper |
| resolve | live Shopify resolve adapter (injected) |
| build_manifest | `nta-betta-shopify-batch-v1` manifest + SHA-256 binding |
| execute | existing `betta_shopify_batch.py` (dry-run unless `live_shopify` + policy) |
| telemetry | existing telemetry SQLite (per-call) |
| archive | existing `betta_archive.py` |

Every external step runs through an injectable runner (testable offline). Adapters
are batch-scoped. Live Shopify writes and paid generation are refused unless
explicitly enabled. A dry-run execute returns `AWAITING_LIVE` (no write, no
success claim). Telemetry is recorded as each call occurs and **fails closed** if it
cannot be recorded.

## 2. Live telemetry

`betta_telemetry.record_call` appends one row per call as it happens
(`betta_call_telemetry`): batch, tank, stage, provider, model, attempt, timestamp,
duration, outcome, tokens (when reported), cost + cost source, error, detail. No
usage or cost is invented. `export_calls` writes `<batch>/reports/betta-call-telemetry.csv`,
which the archive gathers automatically. `batch_call_summary` reports calls,
failures, known cost and unknown-cost calls.

## 3. Label identification

The identify adapter normalises tank IDs (e.g. `2 BT 14` → `2BT14`) and accepts ISO
or Australian DD/MM/YYYY dates, using `label_identity` year provenance. Unresolved
tank/date → the fish is quarantined (never guessed); duplicate tank IDs quarantine
every clashing fish. No completed historical batch is reprocessed.

## 4. Historical QA exception analysis — batch `betta-20261010-084538-08z3re`

Both normal QA passes (3BT36, 4BT13) and six owner-accepted exceptions were
reviewed from the preserved per-fish QA receipts.

| Tank | Failed assertions | Classification | Notes |
|---|---|---|---|
| 3BT42 | label, same_identity, scale_markings, tail_fins_pose | **Material** (+ minor label metadata) | blurred/small source; hero fins expanded; label formatting `3BT42` vs `3 BT-42` |
| 3BT46 | label | **Metadata/date** | hero label date 2026 vs source label 2025 |
| 4BT12 | label | **Metadata/date** | hero label date 2026 vs source label 2025 |
| 4BT14 | regional_colour, same_identity, scale_markings, tail_fins_pose | **Material** | introduced blue markings; altered colour/fins |
| 4BT15 | body_anatomy, label, regional_colour, same_identity, scale_markings, tail_fins_pose | **Material** + **label identity mismatch** | hero reads `4BT15`, source label appears `4BT12` |
| 4BT35 | regional_colour, same_identity, scale_markings, tail_fins_pose | **Material** | stronger scale/colour; different fin shape |

Tally: **4 material**, **2 metadata/date**, with two label/identity metadata
components (3BT42, 4BT15). No confirmed QA false positives and no technical errors
were evidenced. All six remain recorded as `PASS_WITH_ACCEPTED_EXCEPTION`; the
original QA reports and owner acceptance are preserved unchanged. Nothing was
converted to a plain pass, and the generation engine/prompt was not changed.

Policy consequences for V2.2:
- label/date mismatches are metadata issues to resolve deterministically (year
  provenance), not image-fidelity failures;
- genuine appearance discrepancies are never auto-accepted and must be quarantined
  unless the owner records a scoped exception.

## 5. Supervised acceptance plan (to run only after owner approval)

One supervised run through the unified orchestrator (not manual script
coordination), using the currently waiting photographs as a fresh batch.

To be presented before any paid generation or Shopify write:
- Exact batch identity and fish count (from a read-only identification pass).
- The Shopify products that would be updated (exact Product/Variant/Location).
- Expected image-generation cost and retry budget (per fish and per batch).
- Proposed inventory transitions (from → 1), with the guarded stock rules.
- Policy scope (title, arrival date, hero+original media, guarded inventory only).
- Rollback/recovery plan.

After approval: run `process_batch`; independently verify Shopify; then re-run in
resume mode and confirm zero duplicate Shopify writes and zero duplicate inventory
adjustments.

## 6. Zero-touch activation checklist (owner approval required)

1. Complete one supervised acceptance run (section 5).
2. Validate Shopify idempotency via a resume re-run (no duplicate mutations/stock).
3. Confirm archive completion and destination SHA-256 for that run.
4. `betta_policy.py init`; `grant <manifest-sha256> --receipt ...`; then
   `set-enabled true` and `set-paid-generation true` (only if paid generation is
   approved for unattended use).
5. Configure the watcher (launchd) with `--enable`; confirm one automatic batch.
6. Configure Discord completion/exception reporting.
7. Verify restart persistence (state + registry) and document emergency stop
   (`launchctl` unload + `set-enabled false`) and rollback (`git revert`).
